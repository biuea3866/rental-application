## 1. 제품 목표 (Product Goal)

### 1.1 비전

> "거래가 어긋났을 때도 붙잡고, 다시 찾고 싶을 때 쉽게 찾게 한다 — 신뢰 회복과 재방문."

Sprint 1~3에서 회원/상품/대여/결제/리뷰/채팅/정산/관리자 핵심 플로우는 완성됐다. Sprint 4는 **"거래가 실패하거나 문제가 생긴 상황"과 "사용자가 원하는 상품을 다시 찾게 하는 여정"** 을 보강한다.

### 1.2 핵심 가설

| # | 가설 | 검증 지표 |
|---|------|----------|
| H1 | 분쟁 처리 경로가 명시되면 대여 완료율이 개선된다 | 분쟁 오픈 건 중 합의 해결율 ≥ 60%, 재대여 이탈률 < 10% |
| H2 | 부분/전체 환불이 자동화되면 CS 문의가 감소한다 | 결제 관련 CS 문의 주당 -40% |
| H3 | 카테고리 + 가격 + 위치 필터가 있으면 상품 탐색 전환율이 오른다 | 검색 → 상세 진입율 +30%, 상세 → 대여 신청 전환율 +15% |
| H4 | 위시리스트가 재방문을 유도한다 | 위시리스트 추가 사용자의 7일 재방문율 ≥ 60% |
| H5 | 알림 채널 분리 + 설정이 있으면 opt-out 비율이 낮아진다 | 전체 알림 opt-out율 < 5% |

### 1.3 Sprint 4 목표

1. 대여자/등록자가 분쟁(파손/미반납/반품 거부 등)을 오픈하고 관리자가 중재할 수 있다.
2. 분쟁 결과 또는 취소 사유에 따라 부분/전체 환불이 처리되고 정산에 반영된다.
3. 사용자가 카테고리/가격/위치/가용날짜로 상품을 필터링·정렬해 찾을 수 있다.
4. 사용자가 관심 상품을 위시리스트에 저장하고, 가용해지면 알림을 받을 수 있다.
5. 사용자가 알림 종류별 수신 여부를 설정할 수 있다.

## 2. 용어 정의 (Terminology)

| 용어 | 설명 |
|------|------|
| Dispute | 대여 거래 중 또는 후에 발생한 갈등(파손/미반납/오결제 등)의 공식 이슈 레코드 |
| DisputeReason | 분쟁 사유 enum — `DAMAGED`, `NOT_RETURNED`, `LATE_RETURN`, `WRONG_ITEM`, `OTHER` |
| DisputeStatus | 상태 — `OPEN`, `UNDER_REVIEW`, `RESOLVED_REFUND`, `RESOLVED_PARTIAL`, `RESOLVED_REJECTED`, `CANCELLED` |
| Refund | 결제 일부/전체 환불 레코드. Payment-Settlement 양쪽에 보정 반영 |
| Wishlist | 사용자가 관심 상품을 저장한 컬렉션 |
| SearchQuery | 검색 필터 집합 (키워드, 카테고리, 가격 범위, 위치, 기간) |
| NotificationPreference | 사용자별 알림 수신 설정 (chat/rental/settlement/marketing 채널별) |

## 4. 기능 요구사항 (Functional Requirements)

### 4.1 분쟁 처리 (Dispute)

- **FR-1.1** 대여자/등록자는 `RETURNED` 또는 `IN_USE` 상태의 대여 건에 대해 분쟁을 1회 오픈할 수 있다.
- **FR-1.2** 분쟁은 사유(enum), 설명(≤1000자), 첨부 이미지(최대 5장) 필드를 가진다.
- **FR-1.3** 분쟁은 기본 `OPEN` 상태로 생성되며, 관리자가 `UNDER_REVIEW`로 전환 후 해결(`RESOLVED_*`) 상태로 종결한다.
- **FR-1.4** 동일 `rentalId`에 활성 분쟁(`OPEN`/`UNDER_REVIEW`)이 존재하면 신규 오픈 불가.
- **FR-1.5** 분쟁 이벤트 발생 시 양 당사자에게 알림 발송.

### 4.2 환불 (Refund)

- **FR-2.1** 관리자 해결 액션이 `RESOLVED_REFUND` → 전체 환불, `RESOLVED_PARTIAL` → 부분 환불(금액 지정).
- **FR-2.2** 환불은 Payment 레코드에 `Refund` 연결로 기록되며, 대여가 이미 정산된 경우 `Settlement` 보정 레코드를 생성한다.
- **FR-2.3** 환불 처리는 `RefundProcessingService`에서 Payment Gateway(PG) 부분환불 API를 호출한다. **Port-Adapter 패턴** 필수.
- **FR-2.4** 환불 실패 시 분쟁 상태는 유지되고 관리자에게 알림 발송 (자동 재시도 없음 — MVP).

### 4.3 검색 고도화 (Discovery)

- **FR-3.1** 필터: 카테고리(다중선택), 가격 범위, 위치(시/구), 가용 기간(from~to).
- **FR-3.2** 정렬: 최신순 / 가격 낮은순 / 가격 높은순 / 평점 높은순 / 인기순(대여 횟수).
- **FR-3.3** 검색 API는 QueryDSL 기반 동적 쿼리로 구현 (Sprint 4 범위에서는 DB 검색, Elasticsearch 도입은 별도 ADR로 평가).
- **FR-3.4** 페이지네이션 기본 20건, 최대 100건.

### 4.4 위시리스트 (Wishlist)

- **FR-4.1** 사용자는 상품을 위시리스트에 추가/제거할 수 있다.
- **FR-4.2** 한 사용자가 동일 상품을 중복 추가할 수 없다 (UNIQUE 제약).
- **FR-4.3** 상품이 `AVAILABLE` 상태로 전이되는 이벤트를 구독하여, 해당 상품을 위시리스트에 담은 사용자에게 알림 발송.

### 4.5 알림 설정 (Notification Preference)

- **FR-5.1** 사용자는 채널별(chat / rental / settlement / marketing) 알림 on/off 설정 가능.
- **FR-5.2** 알림 발송 직전 `NotificationPreference` 조회 후 off면 발송 스킵.
- **FR-5.3** 기본값: chat/rental/settlement = ON, marketing = OFF.

## 5. 비기능 요구사항 (Non-Functional)

| 항목 | 목표 |
|------|------|

| 위시리스트 조회 | p95 < 200ms |
| 테스트 커버리지 | BE/FE 각 95% 이상 (기존 기준 유지) |
| 보안 | 분쟁 첨부 이미지는 당사자/관리자만 조회 가능 |

## 6. 수락 기준 (Acceptance Criteria)

### 6.1 분쟁 처리
- [ ] 대여자가 `RETURNED` 대여에 대해 분쟁 오픈 시 `Dispute(OPEN)` 생성, 양쪽 알림 수신
- [ ] 활성 분쟁 존재 시 동일 rentalId 두 번째 오픈 → 409 응답
- [ ] 관리자가 `RESOLVED_PARTIAL` 처리 시 지정 금액이 환불되고 정산에 보정 반영

### 6.2 환불
- [ ] 전체 환불 시 Payment.refundedAmount == Payment.amount
- [ ] 부분 환불 반복 시 누적 환불 ≤ 원결제 금액 검증
- [ ] PG 호출 실패 시 분쟁 상태 유지 + 관리자 알림

### 6.3 검색
- [ ] 카테고리=A,B + 가격 10000~50000 + 지역=서울 강남 + 기간=05/01~05/05 필터 조합이 정상 동작
- [ ] 인기순 정렬이 완료된 대여 건수 기준으로 정렬됨
- [ ] 응답 시간 p95 < 500ms (Testcontainers + k6 부하 테스트)

### 6.4 위시리스트
- [ ] 중복 추가 시 409
- [ ] 상품 `AVAILABLE` 전이 이벤트 수신 시 담은 사용자 전원에게 알림 1건 발송

### 6.5 알림 설정
- [ ] 설정 off 상태에서 해당 채널 알림 미발송
- [ ] 새 가입자 기본값이 PRD 명세대로 설정됨
